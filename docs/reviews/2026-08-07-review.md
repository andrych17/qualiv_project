## 1. Kredensial produksi & staging ter-commit ke git — 🟢 False positive sementara (2026-08-07, dikonfirmasi user)

> User: nilai di `_env_production` / `_env_staging` saat ini bukan kredensial produksi asli — placeholder/sementara. Jadi remediasi rotasi di bawah **belum relevan** sampai nilai asli beneran dipakai. Tetap dicatat karena begitu isinya jadi kredensial real, langkah remediasi ini langsung berlaku.

**File:** `_env_production`, `_env_staging` (keduanya *tracked* — hanya `.env` yang ada di `.gitignore`)

Isi yang terekspos:

- Password PostgreSQL produksi (`netpgprd1`) dan development (`netpgdev1`)
- Password Redis produksi dan staging
- `APP_KEY`

Masalah tambahan:

1. **`APP_KEY` produksi dan staging identik.** Cookie sesi atau signed URL yang dibuat di staging bisa dipalsukan dan berlaku di produksi.
2. **Staging jalan dengan `APP_DEBUG=true`** di host publik (`staging-erp.nusaevo.com`) → stack trace dan isi env terekspos pada error apa pun.

**Remediasi (urut):**

1. Rotasi password Postgres (`netpgprd1`, `netpgdev1`), password Redis, dan **kedua** `APP_KEY`.
   Rotasi `APP_KEY` membatalkan semua sesi aktif dan merusak kolom bercast `encrypted` — periksa dulu apakah ada kolom terenkripsi sebelum rotasi produksi.
2. `git rm --cached _env_production _env_staging`, tambahkan ke `.gitignore`, commit.
3. Riwayat git masih menyimpannya. Jika repo ini pernah ada di luar mesin lokal, anggap kredensial lama sudah publik terlepas dari rewrite history.
4. Buat `APP_KEY` terpisah per environment. Set staging `APP_DEBUG=false`.

## 2. Aksi tulis dan hapus hanya membutuhkan izin READ

**File:** `app/Http/Middleware/EnsureMenuPermission.php:41`

```php
return match ($action) {
    'create', 'store' => 'create',
    'edit', 'update'  => 'update',
    'destroy'         => 'delete',
    default           => 'read',   // ← semua method lain jatuh ke sini
};
```

Pemetaan berbasis **nama method controller**. Method apa pun di luar lima nama itu hanya butuh izin `read`.

Route yang terdampak:

| Route | Method controller | Izin yang benar-benar dicek |
|---|---|---|
| `*/bulk-destroy` (Inventory, Legal, Projects, Config Menus/Groups/Consts/Serials/Users) | `bulkDestroy` | read |
| `PATCH issues/{issue}/status` | `updateStatus` | read |
| `PATCH issues/{issue}/assignee` | `updateAssignee` | read |
| `PATCH consts/{c}/quick-update` | `quickUpdate` | read |
| `POST issues/{issue}/attachments` | `storeAttachment` | read |
| `DELETE issues/{issue}/attachments/{a}` | `destroyAttachment` | read |

**Dampak:** user read-only dapat menghapus massal seluruh inventory item, legal case, config user, dan project.

**Perbaikan:** jadikan HTTP verb sebagai fallback, bukan `read`.

```php
private function neededPermission(Request $request): string
{
    return match ($request->route()?->getActionMethod()) {
        'create', 'store' => 'create',
        'edit', 'update'  => 'update',
        'destroy'         => 'delete',
        // Method non-resource (bulkDestroy, updateStatus, quickUpdate, …) —
        // pakai verb, jangan pernah default ke 'read' untuk request yang menulis.
        default => match ($request->method()) {
            'DELETE'               => 'delete',
            'POST'                 => 'create',
            'PUT', 'PATCH'         => 'update',
            default                => 'read',
        },
    };
}
```

## 3. Filter kolom arbitrer di async search — ✅ Selesai (2026-08-07)

**File:** `app/Services/AsyncSearchRegistry.php:81`

```php
$extraFilters = $request->except(['q', 'entity', 'limit', 'selected_id', 'page']);
// …
foreach ($extraFilters as $col => $val) {
    $query->where($col, $val);   // ← $col dari query string, tanpa validasi
}
```

Setiap user terautentikasi bisa memfilter berdasarkan kolom apa pun:
`/api/search?entity=user&<kolom_apa_saja>=<nilai>` — menjadi boolean oracle atas seluruh kolom tabel `users` dan `legal_cases`, sekaligus memasukkan identifier tak tervalidasi ke query builder.

**Perbaikan:** tambahkan parameter `filterable` pada `register()` dan saring:

```php
$allowed = $config['filterable'] ?? [];
foreach (array_intersect_key($extraFilters, array_flip($allowed)) as $col => $val) { … }
```

**Diterapkan:** `register()` sekarang punya param `$filterable = []`. `extraFilters` cuma diterapkan kalau kolomnya ada di allowlist itu — default kosong, jadi kedua entity yang sudah terdaftar (`user`, `legal_case`) otomatis nolak semua extra filter karena belum ada caller yang butuh filter kolom (dicek: gak ada frontend yang pakai `extraParams` ke endpoint ini).

# Ide Perbaikan Jangka Menengah

1. **Izin berbasis verb** (#2) menghilangkan seluruh kelas bug "method controller baru = tak sengaja terbuka" — itulah akar masalahnya, bukan sekadar delapan route yang kebetulan terdampak.
2. **Model otorisasi tanpa Policy tidak akan cukup untuk Legal.** Kerahasiaan per-case adalah kebutuhan dasar kantor hukum. Saat ini setiap user firma melihat semua case. Putuskan sebelum vertical Legal dijual.
3. **Penyimpanan lampiran masih di disk lokal app server** (`config/filesystems.php:70`), sementara CLAUDE.md §7B menetapkan Cloudflare R2. Komentar `ponytail:` menyebut pergantian cukup di driver — kerjakan sebelum tenant berbayar pertama, karena migrasi file retroaktif adalah bagian yang menyakitkan.
4. **Tabel modul kanonik** (rekomendasi #10) sekaligus menjadi sumber untuk `config/tenant_modules.php` dan `CreateModuleSchemas::SCHEMAS`, sehingga ketiganya tidak bisa lagi menyimpang diam-diam.
